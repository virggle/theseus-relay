# 进化路线 · 从 Chatbox 到 Harness

**中文** | [English](ROADMAP.en.md)

> 忒修斯号的最终形态不是聊天框，而是一套**接力运行时**：无状态工人按协议接棒，在有状态的基底上完成长程任务。本文是演进阶梯，每级都停在"最小可运行"，并标注它服务的价值轨道（P1–P6，定义见 [PURPOSES.md](PURPOSES.md)）。

## 方向重定向：从对话接力到蜂巢（2026-09-20）

> 三条已拍板的规则 + 四段以 H 编号的里程碑。**本节取代 v0.2 及其后的排程方式**；旧条目的处置见本节末尾的对照表。

### 根上的那一条：驱动信号换了

**旧：一条用户消息 = 一根棒。** 系统是被动的——用户不再说话，链路就停在那里。所以整个项目只能演示"聊天怎么换人"，接不上"任务怎么自己跑"，这就是它长期形同半吊子的原因。

**新：任何输入事件 = 一根棒，工具返回也算。** 系统第一次可以脱离用户自行滚动。协议侧的定义见 PROTOCOL §2.1。

### 规则一：粒度——一组互不依赖的调用 = 一棒

- 判据：**下一步的行动是否依赖某个工具调用的返回值**（PROTOCOL §2.1）。依赖就交棒，不依赖就在本棒发完
- 确认型返回（写入成功/失败、退出码、影响行数）由基底聚合为一行，**不为每个确认各开一棒**
- 每一次写入必须有可识别的 `write_target`；多棒并发时写目标互不相交，**静态检查，冲突即失败**——这条是确定性规则，归脚本层

### 规则二：审查粒度——阶段级，但阶段不许随缘定义

- 每个阶段产出后跟一根审查棒，不是每根执行棒都跟一根（太贵，且返工信号被绑得过细）
- **阶段粒度 = 让审查棒的输入保持有界的那个粒度**：产物清单能塞进一份简报 + 一个装舱预算。否则审查棒的输入会长成另一个长上下文，直接违反 P2 有界上下文

### 规则三：自我改进蜂（带护栏）

蜂群里有一类棒不产交付物，只优化"分配规则"与"任务板 / 文档系统的结构"；需要多少执行、多少审查、多少计划，配额由它自行分配。三条护栏：

1. **不可改区**：协议四条不变量（PROTOCOL §3）、基底校验器、棒级事务语义——不得直接改，只能提 ADR 由人确认
2. **改进提案必须带前后度量，无证据拒收**——把 §4 的校验思路上移到 meta 层
3. **配额硬上限**（建议先取总棒数的 10–15%，实测标定）——防止种群退化成"全是搞分配的蜂，没人干活"

它的 KPI 不新建：遥测与成本双账本（v0.1.2）+ 将来的 retention（v0.1.4）就是来源。**这也是它排在 H3 的原因：度量没落地之前，它只会空转。**

### 四段里程碑

| 阶段 | 内容 | 判成标准 |
|------|------|---------|
| **H0** | 单链步进：批处理棒语义 + 返回值两类处理（PROTOCOL §2.1） | 20 步任务跑完，全程无棒内 ReAct 循环，面板逐步可见 |
| **H1** | 扇出汇聚：`write_target` + 写分区静态检查 + join / 超时 / 部分失败 | 三路并行 → D 汇总，冲突能被引擎拒绝 |
| **H2** | 阶段级审查 + 决策层（先用规则桩占位，再换只返回概率分布的决策类模型） | 每阶段一次审查；每次决策延迟可接受且 100% 可回溯 |
| **H3** | 自我改进蜂（三条护栏）+ 自延续 | 播一次目标跑到 done，且改进提案自带前后度量 |

### 旧条目的处置对照

| 旧条目 | 处置 |
|--------|------|
| v0.2「循环预算」（6 次往返 / 60% 窗口 / 90 s / 死循环检测 / 收尾预留） | **作废**。棒内不再有循环，整套参数失去作用对象（PROTOCOL §2.1） |
| 不做什么「不做多棒并行」 | **解除**。并行是蜂巢的定义；写冲突改由各棒 `write_target` 互不相交的静态检查约束（H1） |
| v0.3 基底化 | **提升为前置**。棒数变多，简报若不降级为"指针 + 意图"，成本与延迟双重爆炸——它不再是"以后再说" |
| v0.4 审查棒 | 粒度改为**阶段级**（规则二）；审查棒"结构性地没看过写作过程"这一优势不变 |
| v0.5 协议独立 | 不变，并入 H2 / H3 |
| R1（共享计数器缺陷） | **被 H0 结构性消解**：棒内不再有三类调用抢同一份预算；H0 之前它在 v0.1 代码里仍是真实缺陷 |
| 交叉点「约 35 棒」 | **失效**（按旧粒度标定），H1 之后重标，重标前不得引用 |
| 度量层 v0.1.3–v0.1.7 | 不变，且新增一层意义：它们是自我改进蜂的 KPI 来源 |

## v0.1 对话接力（当前，已实现）

> 服务轨道：P1 成本（有界输入）· P3 审计（实况面板）· P4 事务（棒级故障隔离）

- 结构化简报 + 累积压缩 + 反占位符
- 翻日志（log-as-memory，按需检索）
- JSON 协议 + 截断抢救 + 反拖延
- 后台实况：每棒输入/输出/检索全程可审计

**已验证的性质**：上下文有界（成本恒定）、棒级故障隔离、身份连续性由协议保证。

## v0.1.1 基底校验器（已实现）

> 服务轨道：P4 事务性 · P3 审计

把 PROTOCOL.md §4 的五项机械校验从纸面落进代码：四节齐全、无占位符、预算内、决策只增不删、指针有效。校验不过 → 拒收重派（§6）。

为什么它排在工具棒前面：**反占位符、反拖延这些实测陷阱，目前全部靠提示词约束（模型自觉）**。校验器是第一个"基底比模型可靠"的组件，成本极低（纯正则 + diff），却把简报质量从概率问题变成确定性问题——后续棒级事务、质量门、协议独立都建立在它的存在之上。

**落地情况**：`src/validate.js` 五项纯函数校验 → `relay.js` 拒收重派（每棒 1 次，仍不过则兜底摘要并标 `rejected`）→ 面板显示校验错误 → `npm test`（node:test，13 项）。无 key 联调见 TESTS.md §C。

**待修正**（详见文末「修正与前置」）：R5 条目数按行计数会误拒；R7 兜底简报只记录不拦截。

> **v0.1.2–v0.1.7 构成「度量与多目的层」**：与 v0.2 工具棒无硬依赖，可交错推进；每项独立停在"最小可运行"。顺序约束统一见文末「修正与前置」§执行顺序——其中两项与直觉不同：v0.1.5 的 L0 指针形态依赖 v0.3 的落盘规则（在此之前 L0 退化为硬压缩档）；检索质量（F1）须先于 v0.1.4 落地，否则衰减探针无法区分「检索没给」这类失败。**补充（2026-09-20）**：度量层还是 H3 自我改进蜂唯一的 KPI 来源，别把它们当成可有可无的装饰。

## v0.1.2 遥测与成本双账本

> 服务轨道：P1 成本 · P3 审计

- 每棒遥测落会话存储：input/output tokens、latency、模型、翻日志次数、salvage/rejected 事件
- 面板新增**成本双账本**：同一会话累计两条曲线——实际接力成本 vs 模拟单体成本（按当前模型价目 × 全历史重读，含前缀缓存读价）
- 为什么它重要：P1 从论战变成面板上的实时数字。短会话输、长会话赢，都如实显示——输了不藏着，是这条轨道的可信度来源

判断标准：面板能实时回答"这个会话若走单体架构，到此刻已花费多少"。

**落地情况**：`src/pricing.js`（价目表 + 单体基线口径 + token 粗估）→ `relay.js` 每棒遥测（token、延迟、模型、翻日志次数、salvage/rejected/重派）→ `/api/state`、`/api/turn` 返回 `cost` 序列 → 后台面板「成本双账本」卡片 + 双折线。`tests/cost.test.js` 手算校验收支，并锁死一个事实：**按当前口径，两棒会话接力更贵，约 35 棒后反超**——输了照样显示在面板上。（**2026-09-20 注**：该数字按旧粒度标定，粒度改了之后失效，重标前不得作为结论引用。）

**待修正**（详见文末「修正与前置」）：R3 账本丢弃了已采集的 `cached` 字段，接力成本被系统性高估；R4 简报夹在固定内容中间，449 字固定内容永久命不中前缀缓存。两项同属本节口径，须一次改完并重出交叉点。

## v0.1.3 跨会话引导

> 服务轨道：P6 持久化 · P5 调度

- 新会话可导入上一会话终局简报的「决策 + 用户画像」两节作为初始简报
- 面板支持导出完整简报链 JSON——人类可读、模型无关
- 为什么它重要：简报链从会话内工件升格为跨会话记忆载体。这是 schema 版本化（v0.5）之外，证明简报可迁移的最小实验

判断标准：关掉浏览器、开新会话导入简报链后，模型能答对上一会话已定的决策。

## v0.1.4 衰减探针

> 服务轨道：P2 稳定性 · P6 持久化

- 每 10 棒自动做一次召回抽查：从基底 log 抽 5 个事实问句，独立调用作答，与原文比对，产出 `retention_rate`
- 为什么它重要：把诚实清单（PROTOCOL.md §8）里"长程衰减无度量"的自白变成可观测指标；同时是 L2 装舱（v0.1.5）的触发传感器——retention_rate 跌破阈值时，下一棒自动升档

判断标准：retention_rate 成为面板常驻指标，且能区分"简报没写"与"模型没用"两种失败。

## v0.1.5 简报带宽分级

> 服务轨道：P1 成本 · P2 稳定性 · P5 调度

- 简报分三档：**L0** = 400 字指针简报（小模型/杂务棒）；**L1** = 800 字全简报（现行默认）；**L2** = 简报 + 基底日志摘录包（大窗口模型的质量模式）
- 基底按下一棒模型的申报上下文预算装配输入；翻日志从"每棒 2 次探照灯"升级为"按预算装舱"
- L0 的指针形态依赖 v0.3 落盘规则（已落盘 → 随时可抛）；在此之前 L0 退化为硬压缩档
- 为什么它重要：模型能力差异从威胁变成调度维度——同一份协议，按接棒者配不同带宽

判断标准：同一会话内不同棒按规则拿到不同档位输入，输出质量无感。

## v0.1.6 基准双轨

> 服务轨道：P2 稳定性 · P1 成本

- benchmark.html 新增**协议基准模式**：同样题目双轨跑——(a) 接力链 (b) 单体长上下文，各在第 30/60/90 轮插入，自动判分出曲线
- 为什么它重要：P2 的核心证据生产器。"新鲜上下文在第 N 轮的质量优势"一旦量化，就是单体架构给不出的差异化卖点；同一批运行顺带产出同场景成本差，喂 P1 的双账本

判断标准：一键产出双轨"质量-轮数"曲线。

## v0.1.7 模型路由表（玩具版）

> 服务轨道：P5 调度 · P1 成本

- 设置页允许规则："含工具调用的棒用模型 X，纯对话棒用模型 Y"；面板显示每棒实际使用的模型
- 为什么它重要：v0.5 跨模型接力的预演——先在对话场景证明"换模型接棒对输出质量无感"（v0.3 判断标准的前置实验），再谈成本调度

判断标准：按规则混用两个模型跑完 50 棒会话，面板全程标注每棒模型。

## v0.2 工具棒（= H0，待按新粒度重写）

> 服务轨道：P4 事务性（副作用账本）· P1 成本（任务级预算与震荡检测）· P2 稳定性（有界输入）

- ACT 阶段发出工具调用请求（文件读写、命令执行、搜索）
- 新增简报第五节：**副作用账本**——本棒执行过的不可逆操作逐条列出，下一棒接手前必须知道"世界上已经被改变了什么"
- 工具权限按棒授予（读写分离、危险操作白名单）
- **确定性质量门（backpressure）**：产物先过测试 / lint / build——零 token、零偏见、每次必跑；不过则当场重派，不进审查棒
- **棒级粒度（2026-09-20 重写）**：取消棒内 ReAct 循环，改用 PROTOCOL §2.1 的静态判据——**下一步是否依赖某个调用的返回值**。原「循环预算」那一整套参数（6 次工具往返 / 60% 窗口 / 90 s / 死循环检测 / 收尾预留）**随之作废**。工具棒因此反而好写：不再需要一套必须实测标定的动态预算体系
- **写目标与写分区**：每次写入须带 `write_target`；多棒并发时各棒写目标必须互不相交，由基底静态检查。这是本节唯一新增的护栏
- **任务级预算与震荡检测**：棒数上限、单任务成本上限（复用 v0.1.2 遥测）——注意它们现在是**任务级**的，不再按单棒计；决策震荡（被否方案被重提）由基底比对决策账本检测并告警（PROTOCOL.md §6）

关键设计：**工具调用的证据落基底，工具调用的意图进简报。** 工人无状态，但世界有状态。

判断标准：一个 20 步任务全部跑完，全程无棒内循环，面板能逐步显示每棒的调用与接棒原因；且上述「证据落基底」必须可验证——工具长输出以「摘要 + 可取回引用」进入简报，全文只落基底，否则"上下文有界"在工具棒上立刻失效。

## v0.3 基底化（H0 的前置，不再是可选项）

> 服务轨道：P1 成本（简报变薄）· P6 持久化（真状态落盘、记忆分层）

- 简报从 prose 降级为指针：状态文件路径、任务列表 ID、SSOT 文档位置
- 真状态全部落盘，简报只记"指针 + 为什么 + 下一步"；§2.1 之后还要记"尚未兑现的意图"
- **落盘规则即压缩规则**（PROTOCOL.md §3 不变量 4）：已落盘 → 简报留指针、随时可抛；未落盘 → 唯一副本、绝不丢。压缩时不做临场判断
- **任务板**：真状态的组织形式是任务板文档（每张任务卡含 `write_target`）。它既是拼接并保证写分区不相交的依据，也是 H3 自我改进蜂的优化对象
- **记忆分层**：项目记忆落各自项目文件夹（SSOT 文档），跨项目可复用的知识沉淀为 skill 按需调用——项目间天然隔离，不占简报预算
- 简报字数上限随之下调（如 400 字）——越薄越稳，重建成本越低

**为什么它升级为前置（2026-09-20）**：棒数会因为 §2.1 的粒度成倍增加，每棒都要付一次"读简报 + 写简报"的固定开销。简报不降为指针式意图包，成本与延迟会双重爆炸。

判断标准：当"换个模型接棒"对输出质量无感时，这一级就算成了。

## v0.4 审查棒与棒级事务（粒度改为阶段级）

> 服务轨道：P4 事务性（棒级事务）· P2 稳定性（结构性无偏审查）

- **阶段级审查**：执行棒产出阶段成果后，由一根审查棒复核，而不是每根执行棒配一根（规则二）。阶段粒度 = 让审查棒的输入保持有界的那个粒度
- 审查棒的结构性优势：**它真的没看过写作过程**——无沉没成本、无所有权偏见，这是单 Agent 架构造不出的审查者
- **分工原则**：确定性质量门（v0.2）拦得住的不交给审查棒——LLM 审查只做语义问题：命名、设计一致性、"做的是不是问的事"。便宜的确定性检查在前，贵的概率性审查在后
- 棒级事务：审查不通过 → 回滚到上一份简报重派，失败的棒不留痕迹

## v0.5 协议独立

> 服务轨道：P5 调度（跨模型接力）· P6 持久化（可迁移 schema）

- 简报 schema 版本化（`brief_schema: 1`），可校验、可迁移
- 棒实现与基底实现解耦：任何 runner（CLI、服务、别的 harness）实现同一份协议即可互接
- 终极形态：**跨模型接力**成为成本调度手段——杂务棒用便宜模型，关键棒换强模型，协议保证无损交接

### R1 为什么排第一

R1 不是"少答一轮"那么简单。它抛错的位置在 `runTurn` 返回**之前**，而 log 与 batons 的写入都在其后（`server.js` 的 `/api/turn` 分支），所以一次触发同时打开三处空洞：回复被丢弃、**用户那句话不进入 log**（log 是 PROTOCOL §5 定义的档案库、P6 的记忆底座）、面板看不到该回合发生过。错误信息还把校验拒收误报成"翻日志次数超限"。在 R1 修好之前，任何度量——v0.1.2 账本、v0.1.4 衰减探针、v0.1.6 基准——都可能被静默吞掉的回合污染。所以它先于一切度量项。

### R3 与 R4 为什么必须一起改

两项都作用在 v0.1.2 的成本口径上。R3 让接力侧拿到它实际能拿到的缓存折扣（用端点回传的真实 `cached`，不引入假设）；R4 让能拿到折扣的固定部分从 537 字涨到 1016 字——实测固定内容共 1016 字（简报前 537 / 简报后 449），每棒 system prompt 1786 字，重排后约省 19% 输入侧成本，且是纯换序、零协议改动。分开改会让"交叉点约 35 棒"这个已被 TESTS.md §D 锁定的数字出现两个口径，所以一次改完、重出交叉点、同步更新测试锁定值。**2026-09-20 追加**：真正的口径变更来自粒度调整（PROTOCOL §2.1），所以合理的顺序是先重标定粒度，再改 R3 / R4，否则交叉点会被重标两次。

### F1 为什么是 v0.1.4 的前置

v0.1.4 的判据要求衰减探针能区分「简报没写」与「模型没用」。检索不可信时会多出第三种失败——「检索没给」——它会把前两种判据一起污染（当前 `searchLog` 是裸 2-gram，且每行 log 都带 `【第N棒·用户】` 前缀，查"用户偏好"时 `用户`/`助手` 会命中所有行，排序直接退化）。v0.1.5 的"按预算装舱"依赖更直接：装舱的前提是检索结果可判断相关性。F1 用停用词表 + log 行前缀剔除，**仍然不引入向量库**，与文末「不做什么」第一条一致。

### 已定（2026-09-12）

**① R1 采用「收尾式预算」语义。** 参照其他有额度限额的工具的通行做法：在触到上限**之前**先对当前工作收尾，产出完整回复 + 更新后的简报，并在简报的「进展 / 开放问题」里留下让下一棒继续跟进的口子——**为完成收尾而略微超出预算是被允许的**。这与 PROTOCOL §2.1 已经写下的"触顶不是丢弃：先按不变量 4 把够重要的落盘、把进展写进简报，下一棒从简报继续"是同一件事。**所以 R1 不需要改协议语义，它是 §2.1 的承诺在 v0.1 里从未落地**——§2.1 把上限描述为"2 次翻日志 + 1 次重派"，而代码里这三类调用共用**同一个**计数器，2+1 根本不可能同时发生，且预算耗尽时直接抛错而非收尾。

由此产生两个待实现的口径：

- 预算分「工作额度 + **收尾预留**」两段，收尾预留不可被正常工作轮次占用（否则收尾永远没有预算可用）。
- **推论（实现时确认）**：收尾语义落地后抛错路径基本消失；对真正失败的棒（模型连续返回不可解析输出），**用户消息仍写入 log**——用户确实说过这句话，档案库不该有洞；不落盘的只是该棒的产物（reply / handoff 不变更）。这使 §5 的档案完整性与 §6「失败棒从未存在」（指产物）不再冲突。

**② R7 拆成两半。** (a) 可见性——兜底结果与 `validation` 错误必须在面板可见——不依赖任何数据，随批次 3 落地；(b) 是否让兜底也重试一次，等实测看到兜底与校验拒收的真实发生率再定。

**③ F1 边界确认。** 停用词表与 log 行前缀剔除都算在「不做什么」第一条"不引向量库"的安全区内，F1 在该边界内实现。

## 不做什么

- 不做向量数据库：检索需求是"找回一句说过的话"，n-gram 够用，复杂度留给基底
- ~~不做多棒并行：接力是串行语义，并行是另一个协议的事~~ → **已解除（2026-09-20）**：并行是蜂巢的定义；写冲突改由各棒 `write_target` 互不相交的**静态检查**约束（「方向重定向」H1）
- 不做流式输出：一次输出完整 JSON 是抢救器能工作的前提，宁可等待
- 不做提示词层的行为约束（能用基底校验器表达的）：规则放 harness 不放 prompt——模型会作弊，脚本不会
- **不让决策类模型替代基底校验器**（2026-09-20 新增）：决策层只能承接"脚本表达不了的有限选项判断"，且输出必须落基底日志；棒级事务的 commit 条件永远是脚本
- 不为单一轨道加特例代码：任何新特性必须服务 ≥2 条轨道（PURPOSES.md §9），单一轨道需求进 backlog 冷冻
